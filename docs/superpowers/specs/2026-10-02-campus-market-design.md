日期：2026-11-06（v8：订单超时释放、商品编辑、聊天轮询与分页；v7：图片轮播与首页分页；v6：订单页卡片与二次确认；v1–v5 见 HANDOFF.md 变更历史）
课程：数据库原理作业
目标：开发一个包含数据库的可运行软件系统（Python + SQLite 的校园二手交易平台）

## 1. 项目概述

校园二手交易平台，面向校内学生。每个登录用户既可以发布闲置商品（当卖家），也可以搜索下单（当买家），身份由数据关系体现而非固定角色字段：发布过商品就是卖家（`items.seller_id`），下过订单就是买家（`orders.buyer_id`）。卖家发布商品并定价，买家按商品名搜索、按价格区间和分类筛选，下单后需**卖家接单**，双方约定见面时核对订单里的 6 位交易码，之后**卖家确认已交付、买家确认已收货，双方都确认交易才完成**；「待接单」「待交付」阶段双方任一方都可取消。不限品类，覆盖教材、数码、宿舍用品等校园常见闲置物。

说明：v1 采用「任一方确认即完成」的简化流程，问题是**一个人就能把交易从下单推到完成**——买家点一下「确认完成」，钱货两清的责任全在一个人身上，答辩演示时经不起追问。v6 改为双向确认：卖家不接单订单无法推进，买家不确认收货订单无法收尾，任何一方都不能替代对方。代价是不做资金托管（个人主体开不了微信支付商户号），用「交易码 + 双方确认」替代「确认收货后打款」，作为线下交付的电子凭证。

作业硬性要求：（1）可以运行；（2）包含数据库，数据自行设计创建。

## 2. 技术栈

- Python 3.12（原作者环境）；代码无版本相关逻辑，3.13 同样可跑
- Flask（网页应用，服务端渲染 HTML）
- SQLite（Python 标准库 `sqlite3`），原生 SQL，不使用 ORM
- 密码存储：`werkzeug.security` 哈希，不存明文
- 运行依赖只有 Flask；测试用标准库 `unittest`，不引入 pytest
- 金额转换用标准库 `Decimal`，不用 float

数据库文件为 `campus_market/campus_market.db`。首次运行自动建库建表并写入示例数据；若文件已存在则不重复初始化。

应用用工厂函数 `create_app(test_config=None)` 创建，数据库路径可由配置注入。测试传入临时文件路径（不用 `:memory:`，因为 SQLite 的内存库每个连接互相独立，多连接下不可用）。

**SQLite 外键必须开启**：SQLite 默认 `foreign_keys=OFF`，外键约束形同虚设。`database.py` 每次建立连接后立即执行：

```sql
PRAGMA foreign_keys = ON;
```

**连接的事务控制**：Python `sqlite3` 默认 `isolation_level` 会隐式开事务，直接执行 `BEGIN` 可能报 "cannot start a transaction within a transaction"。连接统一设 `isolation_level=None`（关闭隐式事务），事务由业务代码手动控制：`BEGIN IMMEDIATE` 开启、`COMMIT` 提交、`try/except` 中 `ROLLBACK` 回滚。`BEGIN IMMEDIATE` 直接拿写锁，避免并发时的锁升级死锁。

## 3. 数据库设计

四张表。建表时声明主键、外键（`ON DELETE RESTRICT`）、非空、CHECK、DEFAULT 约束。系统无删除用户 / 商品的功能，外键用 RESTRICT，防止意外级联删除。

金额一律用 `INTEGER` 存「分」，避免 REAL 浮点精度问题。界面按元录入展示（最多两位小数）。**先用正则 `^\d+(\.\d{1,2})?$` 校验，再用 `Decimal` 解析字符串乘 100 取整，不用 float 运算**（`float('19.99')*100` 有精度风险；不预校验则 `Decimal('19.999')*100` 截断丢精度）：

```python
if not re.fullmatch(r"\d+(\.\d{1,2})?", user_input):
    raise ValueError("价格格式不合法")
cents = int(Decimal(user_input) * 100)   # '19.99' → 1999
if cents <= 0:
    raise ValueError("价格必须大于 0")   # 正则放行 '0'/'0.00'，应用层拦住，不把问题推给数据库 CHECK
```

时间：`created_at` 存 UTC（`DEFAULT (datetime('now'))`，ISO8601）。**展示转换在 Python 侧统一做**（从数据库读出后转成 UTC+8 的字符串再传给模板），模板里不写时区逻辑。

### categories（分类）

| 字段 | 类型 | 约束 |
|---|---|---|
| id | INTEGER | 主键 |
| name | TEXT | 唯一、非空 |

七个固定分类：教材书籍、手机数码、数码配件、宿舍生活、交通出行、服饰运动、其他闲置。

### users（用户）

| 字段 | 类型 | 约束 |
|---|---|---|
| id | INTEGER | 主键 |
| username | TEXT | 唯一、非空 |
| password | TEXT | 非空（哈希值） |
| contact | TEXT | 联系方式（微信 / 手机号），**允许为空** |
| openid | TEXT | 微信用户唯一标识，**允许为空**（网页注册的用户没有） |
| created_at | TEXT | 非空，默认 `datetime('now')`（UTC） |

`openid` 上有唯一索引（`idx_users_openid`）。SQLite 唯一索引允许多个 NULL，所以网页注册的
用户不受影响。微信登录首次进入时自动建号：用户名用「同学 + 随机 6 位」占位，`password`
留空——空密码在登录接口里被显式拒绝，不能靠「哈希校验失败」这条兜底来防
（哈希函数对空串不会抛错，必须显式判断）。

无角色字段。用户是买家还是卖家由 `orders.buyer_id`、`items.seller_id` 的引用关系决定，一个账号可以同时具备两种身份。

用户名规则：入库前去除首尾空格，去空后非空；**区分大小写**（SQLite TEXT 比较默认区分大小写，`Alice` 与 `alice` 是两个用户），文档写明即可，不做大小写归一。

### items（商品）

| 字段 | 类型 | 约束 |
|---|---|---|
| id | INTEGER | 主键 |
| title | TEXT | 非空（商品名，搜索字段） |
| price | INTEGER | 非空，CHECK price > 0（单位：分） |
| condition | TEXT | 非空，CHECK condition IN ('全新','九成新','八成新','有使用痕迹') |
| description | TEXT | 商品描述 |
| status | TEXT | 非空，CHECK status IN ('在售','已预订','已售','下架')，默认 '在售' |
| category_id | INTEGER | 外键 → categories.id（RESTRICT），非空 |
| seller_id | INTEGER | 外键 → users.id（RESTRICT），非空 |
| created_at | TEXT | 非空，默认 `datetime('now')`（UTC） |

### orders（订单）

| 字段 | 类型 | 约束 |
|---|---|---|
| id | INTEGER | 主键 |
| item_id | INTEGER | 外键 → items.id（RESTRICT），非空 |
| buyer_id | INTEGER | 外键 → users.id（RESTRICT），非空 |
| price | INTEGER | 非空，CHECK price > 0（成交价快照，单位：分） |
| status | TEXT | 非空，CHECK status IN ('待接单','待交付','已完成','已取消')，默认 '待接单' |
| deal_code | TEXT | 非空，CHECK 必须为 6 位数字（面交核对码） |
| accepted_at | TEXT | 卖家接单时间 |
| seller_confirm_at | TEXT | 卖家点「我已当面交付」的时间 |
| buyer_confirm_at | TEXT | 买家点「我收到货了」的时间 |
| cancel_by | TEXT | CHECK cancel_by IN ('买家','卖家','系统') |
| created_at | TEXT | 非空，默认 `datetime('now')`（UTC） |

三个时间字段是双向确认的**证据链**：`accepted_at` 证明卖家响应过，`seller_confirm_at` 和 `buyer_confirm_at` 各自独立记录，两条都在才算成交。「系统」这个取值只用于 v1 迁移过来的历史数据——v1 没记取消方，不伪造。

数据库层用三条 CHECK 兜底状态自洽，让「单人推到底」在数据层面就不可能成立：

```sql
-- 接单时间与状态一致：待交付/已完成 必有；待接单 必无；
-- 已取消 允许有（接过单又被取消，是真实历史，不能抹掉）
CHECK ((status = '待接单' AND accepted_at IS NULL)
    OR (status IN ('待交付','已完成') AND accepted_at IS NOT NULL)
    OR status = '已取消'),
-- 已完成 必须双方都确认过
CHECK (status <> '已完成'
    OR (seller_confirm_at IS NOT NULL AND buyer_confirm_at IS NOT NULL)),
-- 取消方只出现在已取消订单上
CHECK ((status = '已取消' AND cancel_by IS NOT NULL)
    OR (status <> '已取消' AND cancel_by IS NULL))
```

注意第二条 CHECK 正是 v1 的漏洞所在：v1 只要把 status 改成「已完成」就成交，没有任何字段能证明是双方同意的。

**`orders` 不设 `seller_id`**：卖家经 `item_id → items.seller_id` 推导，避免同一事实在两处存储造成冗余和不一致。卖出记录的查询统一为：

```sql
SELECT o.*, i.title, i.seller_id, u.username AS buyer_name, u.contact AS buyer_contact
FROM orders o
JOIN items i ON o.item_id = i.id
JOIN users u ON o.buyer_id = u.id
WHERE i.seller_id = ?
ORDER BY o.created_at DESC, o.id DESC;
```

### 索引

```sql
CREATE INDEX idx_items_market ON items(status, category_id, price);
CREATE INDEX idx_orders_buyer ON orders(buyer_id);
CREATE INDEX idx_orders_item ON orders(item_id);

-- 部分唯一索引：同一商品至多一条「进行中」订单（待接单或待交付），数据库层兜底
CREATE UNIQUE INDEX idx_orders_active_item
ON orders(item_id) WHERE status IN ('待接单','待交付');
```

业务代码的原子更新是第一道防线，这个部分唯一索引是第二道：即使代码有漏洞，重复插入进行中订单也会被数据库拒绝。索引的 WHERE 条件必须同时覆盖「待接单」和「待交付」——如果只写 `= '待接单'`，卖家接单后索引就不再约束该商品，第二个买家可以插一条新的待接单订单，同一个商品就会被两个人同时「订下」。这一条已有专门用例锁定（`test_partial_unique_index`）。

注意该索引只约束进行中的状态：**同一商品可以有多条历史订单**（例如下单 → 取消 → 再下单 → 完成，产生两条订单记录），这是预期行为。

### 示例数据

首次运行写入：7 条分类、约 10 个用户（每人都既买又卖，联系方式有的填有的为空，覆盖空值展示）、约 30 件商品（覆盖各分类、不同价格带、四种状态都有）、若干订单。示例数据保证状态一致：

- 订单「待接单」→ 对应商品「已预订」
- 订单「待交付」→ 对应商品「已预订」（卖家已确认交付、买家还没确认，正好演示半程状态）
- 订单「已完成」→ 对应商品「已售」
- 订单「已取消」→ 对应商品「在售」

## 4. 页面与功能

### 权限模型：登录即可买卖，操作按归属

全员可买可卖，没有固定角色。登录后的权限只看归属关系：

- **查看与操作都按归属**：「我的订单」（buyer_id = 当前用户）、「卖出记录」（商品 seller_id = 当前用户）、「我的商品」（seller_id = 当前用户），自己只能看到和操作属于自己的数据。
- 发布商品、下单：任何登录用户都可以。
- 不能购买自己发布的商品。
- 改价、编辑、删图、下架：只有商品发布者本人。
- 接单、确认交付：只有卖家；确认收货：只有买家；取消：「待接单」「待交付」阶段买卖任一方。
- 超时释放由系统触发，不走任何用户权限。

导航栏常驻：「商品市场 / 发布商品 / 我的订单 / 卖出记录 / 我的商品 / 设置」，登录后导航栏右侧另有「登出」（POST，清 session 后回首页）；未登录显示「登录 / 注册」。导航栏显隐只是展示优化，**权限一律以服务端路由校验为准**，不满足时返回 403 并提示。

### 页面清单

1. **首页 / 商品市场**：分类标签栏（7 类可点，可不选）+ 商品名搜索框 + 价格区间（最低价 / 最高价）+ 排序（最新发布 / 价格从低到高 / 价格从高到低，**服务端白名单**，非白名单值回落默认序）+ 商品卡片列表，页头显示当前结果件数与「清除筛选」。商品卡片显示：封面图（无图时占位）、商品名、价格、成色、分类、**卖家用户名**（不含联系方式，联系方式只在详情页登录后可见）、发布时间（`MM-DD HH:MM`）。**自己发布的商品照常展示，但标题后带「我发布的」标识**——市场是给人逛的，隐藏自己的东西反而无法确认“我发的在别人眼里长什么样”，加标识既能区分又避免误点。三个筛选条件可任意组合，也可只用其一。搜索框留空表示不按名称过滤；价格只填最低价表示「≥ 最低价」，只填最高价表示「≤ 最高价」，都留空表示不限价格。列表**只显示 `status='在售'` 的商品，按 `created_at DESC, id DESC` 排序**（最新发布在前；`created_at` 精度到秒，加 `id DESC` 作第二排序键，同一秒发布也能次序稳定，测试可断言）。URL 传入不存在的 `category_id` 时忽略该筛选条件（按全部分类展示），不报 500。列表**每页 12 件**，底部页码条保留当前全部筛选条件（`q / min_price / max_price / category_id / sort`）；`page` 参数越界（0、负数、超出总页数）或非数字时一律夹回有效范围，不报 400，也不返回空页。计数与列表共用同一套 WHERE 片段（`market._build_filters`），保证「共 N 件」与实际翻页结果一致。
2. **商品详情页**：图片区是**轮播**（`position` 决定顺序），主图区左右切换 + 缩略图条 +「2 / 5」计数，点击图片在新标签打开原图（二手商品要看瑕疵，缩略图看不清）。轮播基于滚动容器 + `scroll-snap`，**不依赖 JS 也能滑动查看**；脚本只接管左右按钮、缩略图跳转、方向键和计数高亮，单图商品不渲染按钮与缩略图，`prefers-reduced-motion` 下取消平滑滚动。之后显示商品状态标签（在售 / 已预订 / 已售 / 下架）。**详情页按状态分级开放访问**（不是任何状态都公开）：
   - 「在售」：任何人可看（含匿名用户，便于浏览市场）
   - 「已预订」「已售」：登录用户可看（便于从订单页跳回查看），匿名访问跳登录
   - 「下架」：**仅发布者本人可看**，其他人一律 404（下架即对他人隐藏）
   「下单，等卖家接单」按钮仅当商品「在售」、且不是自己发布的商品、且已登录时显示；按钮下方用一行小字说明「下单后商品为卖家保留，双方各自确认才完成」，避免用户以为点一下就算买到了。卖家联系方式仅登录后可见；**联系方式为空时显示「卖家未填写联系方式」**。
3. **注册页**：用户名（去首尾空格后非空）、密码（最短 6 位）、联系方式（可不填）。用户名重复时提示已存在。
4. **登录页**：用户名 + 密码。登录失败统一提示「用户名或密码错误」，不区分用户不存在还是密码错，避免枚举用户。
5. **发布商品页**（登录即可）：商品名、分类下拉、价格（元，两位小数）、成色下拉、描述。
6. **我的商品页**：自己发布的商品**卡片列表**（封面缩略图、商品名、价格、状态、发布时间），含状态。「在售」商品可**编辑**（标题 / 价格 / 成色 / 分类 / 描述 / 增删图片，独立页面 `item_edit.html`）、可下架；「已预订」不可编辑下架（订单未完成，改价改名会让买家看到的和谈好的不一致）；「已售」作为成交记录保留，不支持编辑下架；「下架」为终态，**不再提供重新上架**，下架按钮旁提示「下架后不可恢复」。编辑页删图后会把剩余图片的 `position` 重排成 0、1、2…，避免 0~4 的 CHECK 约束留空洞。
7. **我的订单页**：自己作为买家下的单，**含「已取消」订单**，按 `created_at DESC, id DESC`。每条显示商品信息、订单状态与状态说明、**卖家用户名和联系方式**（空时显示「对方未填写联系方式」）。操作按状态给：`待接单` 可取消；`待交付` 可取消、可点「我收到货了」，并显示 6 位面交核对码和双方确认进度；`已完成`「已取消」只读。若商品已被下架（买家无权查看详情），商品标题只显示文本、不渲染详情链接，避免 404 死链。
8. **卖出记录页**：自己作为卖家被下单的商品订单，**含「已取消」订单**（口径与「我的订单」一致，历史都保留），按 `created_at DESC, id DESC`。每条显示商品信息、订单状态、**买家用户名和联系方式**（空时显示「对方未填写联系方式」）。操作按状态给：`待接单` 可「接单」或「拒绝订单」；`待交付` 可「我已当面交付」或「取消交易」，同样显示核对码和确认进度；终态只读。
9. **设置页**：修改联系方式。**本作业设置页不含修改密码**（范围外，答辩可说明；账号系统通常会有，后续可加）。

## 5. 业务规则

- 登录用户都能发布商品、都能下单；未登录只能浏览市场和「在售」商品详情（联系方式除外）。
- 不能购买自己发布的商品（`item.seller_id` 等于当前用户 id）。

### 订单状态机

```
              买家下单                卖家接单              卖家确认交付 + 买家确认收货
  在售商品 ──────────▶ 待接单 ──────────▶ 待交付 ──────────────────────▶ 已完成
                        │                  │
                        │ 任一方取消        │ 任一方取消
                        └──────────────────┴──────▶ 已取消（商品回在售）
```

动作与权限严格对应，每一格都有用例锁定：

| 动作 | 谁能做 | 前置状态 | 结果 |
|---|---|---|---|
| 下单 | 任意登录用户（非卖家本人） | 商品「在售」 | 订单「待接单」，商品「已预订」 |
| 接单 | **仅卖家** | 「待接单」 | 「待交付」，写入 `accepted_at` |
| 确认已交付 | **仅卖家** | 「待交付」且未确认过 | 写 `seller_confirm_at`；若买家已确认则「已完成」 |
| 确认已收货 | **仅买家** | 「待交付」且未确认过 | 写 `buyer_confirm_at`；若卖家已确认则「已完成」 |
| 取消 | 买家或卖家 | 「待接单」或「待交付」 | 「已取消」，记 `cancel_by`，商品回「在售」 |
| 超时释放 | **系统**（无人操作） | 「待接单」且下单已超 2 小时 | 「已取消」，`cancel_by='系统'`，商品回「在售」 |

三条关键约束：

1. **双方确认才成交**。卖家点「我已当面交付」只是写自己的那一半，买家没点收货，订单停在「待交付」；反之亦然。两个确认的先后顺序不限——买家可以先点收货，等卖家点交付时自动收尾。
2. **终态不可逆**。「已完成」「已取消」不接受任何再次操作，重复点交付/收货也会被拒绝（条件更新 `AND seller_confirm_at IS NULL` 命中 0 行即报错）。
3. **权限按角色切开**。买家调交付接口返回 403，卖家调收货接口返回 403，第三方调任何订单接口都 403。服务层与路由层各校验一次，不只靠前端隐藏按钮。

- 商品状态流转与订单联动：下单 `在售 → 已预订`；成交 `已预订 → 已售`；取消 `已预订 → 在售`。

### 超时释放（惰性，不依赖定时任务）

买家下单会把商品锁成「已预订」，卖家长期不理就锁死了——这是二手交易里真会发生的纠纷源头。
对策：**待接单超过 `CM_ORDER_TIMEOUT_MINUTES`（默认 120 分钟）未处理，订单自动取消、商品回「在售」**。

实现上不做 cron，而是在 `app.before_request` 里顺手扫一眼（`trading.expire_stale_orders`）：

- 每个进程最多 30 秒扫一次，页面请求不为此多付一次写库代价；
- 只扫 `status='待接单' AND accepted_at IS NULL` 的订单，**卖家接过单的（待交付）永不超时**——那已经是双方进入交付流程，自动取消会坑掉买家；
- 单笔一个 `BEGIN IMMEDIATE` 事务，一笔坏数据不影响整批；扫描失败一律静默，不能把正常请求带崩；
- 取消方记 `系统`（`cancel_by` 早已允许这个取值），订单卡片会显示「由系统取消」；
- 配置 `CM_ORDER_TIMEOUT_MINUTES=0` 可整体关闭；`python manage.py expire [分钟]` 可手动立即执行一次（给 cron 或演示兜底）。
  演示前若示例数据里的「待接单」订单太旧，`python manage.py refresh-pending` 会把它们的下单时间挪到最近。
- 只有商品发布者本人能改价、下架自己的商品（路由层按归属校验）。
- 商品状态为「已预订」时不可改价、不可下架、不可再次下单；「已售」商品不在市场显示，作为成交记录保留；「下架」为终态，对非发布者隐藏详情。
- 「下架」商品不出现在市场列表，仍可在「我的商品」中看到。

### 下单的原子性（防超卖）与价格快照

两个买家同时下单同一商品时，不能各自先查再改。事务内完成，**成交价从数据库读取，不信任客户端传入的价格**（防止篡改表单价格）：

```sql
BEGIN IMMEDIATE;
SELECT price, seller_id FROM items WHERE id=? AND status='在售';
-- 查不到 → 商品已售/已预订/下架，ROLLBACK 并提示
-- seller_id 等于当前用户 → 不能买自己的商品，ROLLBACK 并提示
UPDATE items SET status='已预订' WHERE id=? AND status='在售';
-- 受影响行数为 0 → 抢占失败（被别人先下单），ROLLBACK 并提示
INSERT INTO orders(item_id, buyer_id, price, status, deal_code)
VALUES(?, ?, ?, '待接单', ?);        -- deal_code 为随机 6 位数字，创建时即生成
COMMIT;
```

`orders.price` 的快照取自上面 `SELECT price` 的结果。同一件商品同一时刻至多于一条进行中订单，由原子更新 + 部分唯一索引双重保证。异常路径一律 `ROLLBACK` 后返回提示，不留半截数据。

### 接单 / 交付 / 收货 / 取消的条件更新

状态流转的每一步都带条件并检查受影响行数，防止重复流转或并发下的错乱：

```sql
-- 卖家接单
BEGIN IMMEDIATE;
UPDATE orders SET status='待交付', accepted_at=datetime('now')
WHERE id=? AND status='待接单';           -- 行数 0 → 非法流转，ROLLBACK
COMMIT;

-- 卖家确认交付（幂等保护：已确认过则 rowcount 为 0）
BEGIN IMMEDIATE;
UPDATE orders SET seller_confirm_at=datetime('now')
WHERE id=? AND status='待交付' AND seller_confirm_at IS NULL;
-- 然后检查对方是否已确认：
SELECT seller_confirm_at, buyer_confirm_at FROM orders WHERE id=?;  -- 均为非空
UPDATE orders SET status='已完成' WHERE id=? AND status='待交付';
UPDATE items  SET status='已售'   WHERE id=? AND status='已预订';   -- 行数 0 → 数据异常
COMMIT;

-- 买家确认收货：同上，只换 buyer_confirm_at 与角色校验
-- 取消（买家或卖家）
BEGIN IMMEDIATE;
UPDATE orders SET status='已取消', cancel_by=? WHERE id=? AND status IN ('待接单','待交付');
UPDATE items  SET status='在售'   WHERE id=? AND status='已预订';
COMMIT;
```

收尾那一步（双方确认后置「已完成」+ 商品「已售」）封装在 `trading._try_complete()` 里，
两个确认动作都调用它，避免两处各写一遍导致一边漏改商品状态。

第一类 UPDATE 行数为 0 是正常业务（重复操作、状态已流转），提示后返回。商品那一步行数为 0 **理论上不该发生**（商品状态本应与订单一致），说明数据被外部改坏：同样 ROLLBACK，返回 500 并提示「数据异常，请稍后重试」，不静默继续、不留半截状态。注意这一条在双向确认下更严格：买家点收货触发收尾失败时，连他自己刚写的 `buyer_confirm_at` 也会一起回滚，订单停在「待交付」，不会留下「买家已确认但订单没成交」的中间态。

## 6. 错误处理

- 登录态用 Flask session，**session 只存 `user_id`**；每个请求从数据库读取用户信息。`app.secret_key` 开发环境用固定常量（生产应改环境变量注入）；`SESSION_COOKIE_HTTPONLY=True`（Flask 默认）；作业不启用 HTTPS，故不设 `Secure` 标志。
- 未登录访问发布、下单、订单、设置等页面时跳转登录页。
- **所有写操作（注册、登录、登出、发布、改价、下架、下单、接单、取消、交付、收货、改联系方式）一律用 POST**，不提供 GET 触发状态变更的入口。
- **路由按归属强制鉴权**，不满足时 403 并提示（不只靠导航栏隐藏按钮）：
  - 非商品发布者提交改价 / 下架 → 403
  - 非订单买家 / 卖家提交任何订单操作 → 403
  - 买家提交「接单 / 确认交付」、卖家提交「确认收货」→ 403（角色校验在服务层，不靠前端隐藏按钮）
  - 对终态订单执行任何操作、对待接单订单确认交付 → 拒绝并提示
  - 非发布者访问「下架」商品详情 → 404
- 所有 SQL 使用参数化查询，防注入。商品名模糊搜索用 `LIKE ... ESCAPE '\'`，用户输入的 `%`、`_`、`\` 先转义，防止通配符干扰筛选。
- 表单校验失败返回页面并提示原因，不崩页：
  - 用户名去首尾空格后非空、密码非空且最短 6 位；用户名重复提示已存在。**并发注册同名用户时唯一约束抛 `IntegrityError`，捕获后同样提示「用户名已存在」，不返回 500**
  - 价格用正则 `^\d+(\.\d{1,2})?$` 预校验后经 `Decimal` 转为分，**应用层校验分值 > 0**（`0`、`0.00` 提示「价格必须大于 0」，不抛数据库 CHECK 错误）
  - 价格区间必须为合法数字；**两端都填时才校验最低价 ≤ 最高价**，只填一端时不比较、直接按单边条件过滤
  - 分类 id 不存在时忽略该筛选（不 500）
  - 下单条件不满足时提示（商品已售 / 已预订 / 下架、买自己的商品等）
- 商品详情页卖家联系方式仅登录后可见，避免对匿名访客公开。
- **已知简化**（答辩可如实说明）：
  - 没有内容安全检测与举报入口：商品文本、聊天消息、图片都是用户生成内容，公网开放给陌生人前必须补 `msgSecCheck` / `imgSecCheck` 或人工审核后台
  - `title LIKE '%关键字%'` 用不了 B-tree 索引，数据量小可接受，不引入 FTS5
  - **没有支付与资金托管**：个人主体开不了微信支付商户号，平台不碰钱，用「6 位核对码 + 双方确认」作为线下交付凭证
  - **订单超时释放已实现**：待接单超过 2 小时未处理自动取消、商品回「在售」，见上文「超时释放」小节。它靠请求级惰性扫描触发，没有任何请求时不会自己跑（真上线应再加一条 cron 调 `manage.py expire`）
  - 没有站内实时推送，聊天靠 **5 秒轮询**增量（`/updates?after=`），不是长连接；商品列表已分页（每页 12），消息已分页（每页 50），**会话列表仍固定取最近 50 个**

### 已加固的部分（安全）

早期版本把 CSRF 防护列为"已知简化"，公网部署后这是实打实的漏洞：攻击者只要让
已登录用户访问一个页面，就能伪造表单替对方下单、改价、确认收货。现已补上：

- **CSRF**：每个会话一个随机 token（`secrets.token_urlsafe`），所有 POST 表单带隐藏字段，
  服务端 `hmac.compare_digest` 比对；对不上返回 400 并提示刷新。接口 `/api/*` 用
  Bearer token，不依赖 cookie，天然免疫，故排除在外
- **登录限流**：同一 IP + 用户名 10 分钟内失败 5 次即暂时锁住，成功登录清零。挡暴力破解
- **会话安全**：`HttpOnly` + `SameSite=Lax`，登录成功与登出都重置会话与 token
- **SECRET_KEY 走环境变量**（`CM_SECRET_KEY`），默认值仅用于本地开发，启动时会打印警告
- **请求体上限 40MB**（`MAX_CONTENT_LENGTH`），防止超大表单撑爆内存
- **生产服务器换成 waitress**（`run.py`），Flask 自带的开发服务器单线程且会泄露调试信息

部署方式与环境变量清单见 `HANDOFF.md` 附录 A。

## 7. 测试

用标准库 `unittest` + Flask test client。`create_app` 支持注入数据库路径，测试每个用例组使用独立临时文件数据库（不用 `:memory:`）。

覆盖链路：

- 注册、登录、登出；用户名首尾空格被去除；`Alice` 与 `alice` 是不同用户
- 任意登录用户可发布商品、可下单（同一账号既买又卖）
- 发布商品、改价、下架；非发布者改价 / 下架返回 403；下架后商品不可再操作
- 搜索（商品名模糊，含 `%` 特殊字符输入）、价格区间筛选（含最低价 > 最高价的非法输入）、分类筛选及组合查询；非法 `category_id` 被忽略
- 市场只显示「在售」商品（已售、已预订、下架均不出现），**按 `created_at DESC, id DESC`，同一秒发布的多个商品顺序稳定**
- 商品详情访问权限：匿名可看「在售」；匿名访问「已预订/已售」跳登录；「下架」仅发布者可看，其他人 404（订单页对无权查看的商品标题不渲染链接）
- 价格输入 `0`、`0.00` 被应用层拒绝（提示「价格必须大于 0」），不是数据库报错；`19.999`、`abc`、`-5` 被正则拒绝
- 并发注册同名用户：模拟唯一约束冲突（`IntegrityError`）返回「用户名已存在」，不 500
- 下单成功后商品变为「已预订」，订单「待接单」并带 6 位数字核对码；订单价格取自数据库（POST 伪造价格不影响成交价）
- 不能买自己的商品；不能重复下单同一商品
- 直接 POST 下单已售 / 已预订 / 下架商品被拒绝
- **并发防超卖的两层验证**：顺序两次下单同一商品第二次失败；直接向 orders 插入第二条同商品「待接单」订单被部分唯一索引拒绝；**「已接单（待交付）」的商品同样不能再被下单**（索引 WHERE 覆盖两种进行中状态）
- **完整生命周期**：下单 → 取消 → 再下单 → 卖家接单 → 卖家交付 + 买家收货，商品终态「已售」，订单表留两条历史订单（验证部分唯一索引不误拦历史）
- **双向确认专项**：
  - 卖家未接单时买家点确认收货被拒，订单仍是「待接单」
  - 卖家点「我已当面交付」后，订单仍是「待交付」、商品仍是「已预订」，必须等买家确认收货才收尾
  - 买家先确认收货、卖家后确认交付，同样能正常收尾（顺序不限）
  - 重复点交付 / 重复点收货被拒绝，不产生重复写入
  - 买家调交付接口、卖家调收货接口返回 403；第三方调四种订单操作全部 403
  - 「待接单」订单在买家页不出现「我收到货了」按钮
- 同一笔订单里，买卖双方页面显示同一个核对码
- 「我的订单」显示卖家用户名与联系方式、「卖出记录」显示买家用户名与联系方式，空时显示「对方未填写联系方式」；「已取消」订单出现在两个列表中并标明取消方
- 非法订单状态流转被拒绝（如对「已完成」订单再取消、对「已取消」订单再确认收货）
- **数据库 CHECK 兜底**：只写一侧确认时间却要置「已完成」被拒；「待交付」缺接单时间被拒；「已取消」缺取消方被拒；核对码不是 6 位数字被拒
- **数据不一致异常路径**：直接改库制造商品状态与订单不符，双方确认收尾时第二个 UPDATE 行数 0 → 事务回滚，返回数据异常提示，且**买家刚写入的确认时间一并回滚**，订单停在「待交付」
- **迁移脚本**（`MigrationTests`）：v1 的「待交易」正确映射为「待接单」、已完成补两侧确认时间、已取消标注「系统」；重复执行直接跳过（幂等）；**迁移后的表结构与 `PRAGMA table_info` / `index_list` 必须与 `schema.sql` 新建的库完全一致**（防止两份 DDL 各自漂移）
- **接口层**（`tests/test_api.py`，43 个用例）：统一信封 `{code,message,data}`、token 鉴权与过期、401/403/404/409 状态码、未配 AppID 时微信登录返回 501、下单 → 接单 → 交付 → 收货全链路、核对码只在「待交付」阶段下发、第三方越权
- 未登录访问受保护页面跳转登录；**登出后访问受保护页面同样跳登录**；越权访问返回 403
- 外键约束生效：删除被商品 / 订单引用的用户应失败（PRAGMA foreign_keys 确实开启）
- 金额元分转换边界：`0.01` → 1 分、`19.99` → 1999 分、`100.00` → 10000 分
- 价格区间只填一端的过滤结果（只填最低价 / 只填最高价），两端都填时的范围过滤
- `created_at` 展示为本地时间（UTC+8）字符串

当前规模：网页端与数据库 **133 个用例**、接口 **43 个用例**，共 176 个，全部通过。

v6 曾实现一套原生小程序（8 个页面），与网页共用 `/api/v1`。**v9 已移除前端源码**
（当初的备份文件 `backup/miniprogram-2026-11-01.zip` 没有随项目一起交接，现已不在仓库内，
若要恢复得重写），原因不是技术问题，而是资质：

- 多用户互相买卖属于「电商平台」类目，个人主体的小程序选不了这个类目
- 该自营类目外的电商平台还需要《增值电信业务经营许可证》（ICP 许可证），要求公司主体
- 只做个体户也不够，审核仍然会按平台模式判定资质

结论：**不做支付并不影响审核，卡点是主体与类目**。个人身份做多用户交易平台，小程序这条路走不通。

**后端 `/api/v1` 保留**：它是无状态的 JSON 接口（Bearer token），网页不使用它，但
H5 或将来有资质后的小程序可以直接复用，不需要重写业务逻辑。接口测试也保留（43 个用例），
保证它不会腐坏。

保留的设计经验，将来若要用：

- **交易规则只有一份**：接口与网页共用 `trading.py` / `market.py`，不存在两套逻辑
- 鉴权用 itsdangerous 对 user_id 签名，30 天有效，无会话表
- 未来接支付：在「卖家接单」与「待交付」之间插入「待支付」状态即可，`_try_complete()` 不用动

## 9. 图片与议价聊天（v7 新增）

### 商品图片

表 `item_images(id, item_id, filename, position)`，一件商品最多 5 张，`position` 决定轮播顺序，
首图即列表封面。文件落本地磁盘 `uploads/items/`，数据库只存文件名。

三条安全约束，缺一条都能出事：

1. **文件名服务端生成**（`{item_id}_{16位随机}.ext`），不含任何用户输入 → 杜绝路径穿越
2. **按文件头校验真实类型**（JPEG `FFD8FF`、PNG `89504E47`、WebP `RIFF....WEBP`），
   不信客户端给的扩展名。只改后缀的 `.exe` 会被拒绝
3. **大小与数量双限**：单张 5MB、每件 5 张，在服务层判断后抛 BizError，不靠前端限制

失败语义要讲究：商品创建与图片上传分两步，图片失败时**不回滚商品**，而是提示
「商品已发布，N 张图片失败」——回滚会让用户重新填一遍表单，体验更差。

### 议价聊天

会话以 `(item_id, buyer_id)` 为单位，`messages` 表存消息，卖家由 `items.seller_id` 推导，
不为会话单独建表（少一层 join，且不会有"空会话"垃圾数据）。

| 字段 | 说明 |
|---|---|
| kind | `text` 普通消息 / `offer` 报价 |
| offer_price | 报价金额（分），仅 `offer` 有 |
| accepted_at | 报价被卖家接受的时间 |
| read_at | 被对方读掉的时间，用于未读计数 |

业务规则：

- 买家可对任何在售商品发起会话；**卖家不能主动开新会话**，只能回复已有的（防骚扰）。
  判断依据是「这个会话是否已有消息」——服务层校验，不靠前端藏入口
- 报价必须 **低于当前标价**，否则提示"直接下单即可"，省一次无效往返
- 卖家接受报价 → 直接改 `items.price` 并写 `accepted_at`。改价沿用商品改价的约束
  （`AND status='在售'`），已不在售则拒绝；同一报价不能接受两次
- 打开会话即把对方消息标记已读，`/messages` 返回未读总数给导航角标
- 第三方读写一律 403（`chat.ensure_member`）。买家也不能和自己聊

数据库层同样加了 CHECK 兜底：`offer` 必须有 `offer_price`、`text` 必须没有；
`accepted_at` 只能出现在报价消息上。

### 记录分页与轮询新消息

- `chat.thread()` 取的是**最近 50 条**（先 `ORDER BY id DESC LIMIT 50` 再翻转成正序）。
  早期实现是「从最早一条取 100 条」，对话超过 100 句后新消息永远刷不出来——这是一个真 bug，
  现在由 `ThreadPagingTests` 锁住。
- 往上翻历史用 `?before=<最早那条的 id>`，页面顶部出现「查看更早的消息」；
  查的是 `id < before` 的同一套条件，坏参数当没传（不 500）。
- 新消息用**轮询**而不是 SSE：`GET /messages/<item>/<buyer>/updates?after=<最后一条 id>`
  返回增量 JSON，页面每 5 秒拉一次，`document.hidden` 时暂停、切回前台立即补一次。
  选轮询的理由：waitress 是同步模型的 8 线程，SSE 会占住线程，而本项目明确保持「全同步、无线程」。
- 轮询同样走 `chat.ensure_member`，第三方拿 403；拉到新消息会顺带标记已读。

### 新增测试

- 图片：上传后列表/详情都带图、非图片文件被拒、超 5MB 被拒、超过 5 张被拒、非本人上传 403、
  上传的文件能被 `/uploads/...` 正常取回
- 聊天：买家开会话、卖家回复、卖家不能主动开新会话、第三方 403、
  报价接受后商品价真的变了、买家不能接受报价、报价不低于标价被拒、非法金额被拒、
  空消息被拒、未读数先增后清零
- 合计 176 个用例（网页 133 + 接口 43）
